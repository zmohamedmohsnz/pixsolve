# PixSolve Project Decisions

This document records implementation decisions that supplement, but never override, `scope-v1.md`.

## Confirmed Decisions

| Area | Decision |
| --- | --- |
| Project intent | Backend engineering portfolio project |
| V1 scope | `scope-v1.md` is final and authoritative |
| Language | JavaScript |
| Runtime | Node.js |
| Module system | ECMAScript modules |
| Image processing | Sharp |
| File storage | Cloudinary |
| Database | MongoDB with Mongoose |
| Local MongoDB environment | Docker container |
| Background jobs | BullMQ with Redis and a separate worker process |
| Planning approach | Kanban-style GitHub Project |
| Milestone | PixSolve V1 |

## Decision Timing

Unresolved implementation decisions will be made when their related issue is refined or implemented. They should not be decided early unless they block current work.

Examples of deferred decisions include:

- File retention and cleanup policy.

When a decision is made, add it to the decision log below. Choose the simplest option that stays inside V1 and demonstrates the intended backend skill.

| 2026-08-31 | Language | Use JavaScript | Project owner preference |
| 2026-08-31 | Storage | Use Cloudinary as the only storage provider | Project owner preference and V1 single-provider constraint |
| 2026-08-31 | Local database | Run MongoDB in Docker | Project owner preference |
| 2026-08-31 | Planning | Defer non-blocking implementation decisions until the relevant issue | Avoid premature design and keep a portfolio-sized V1 |
| 2026-09-02 | Environment configuration | Validate `NODE_ENV` as `development`, `test`, or `production`, default it to `production`, and require `PORT` to be an integer from 1 to 65535 | Keep runtime configuration centralized and fail startup clearly when required configuration is invalid |
| 2026-09-05 | Upload size enforcement | In V1, enforce the 5 MiB image limit with Multer. Early infrastructure-level rejection of oversized request bodies is deferred until after V1. | Multer limits application memory usage but may drain the remainder of an oversized HTTP request; rejecting the network transfer earlier depends on the future deployment topology. |
| 2026-09-06 | Resize behavior | Preserve the source aspect ratio using Sharp's `cover` fit with centered cropping. Produce exactly the requested width and height, allow enlargement, and do not expose fit or crop position as user-selectable V1 options. | Produce predictable output dimensions without distortion while keeping user-selectable resize fit modes outside V1. |
| 2026-09-07 | Compression behavior | Re-encode the image without changing its dimensions or format. Apply Sharp's lossy `quality` setting to JPEG and WebP, and Sharp's palette-based `quality` setting to PNG, which may reduce color detail. Compression aims to reduce file size but does not guarantee a smaller output. | Give the single V1 `quality` option meaningful behavior for every supported format while keeping automatic lossless selection, target-file-size compression, and format-specific controls outside V1. |
| 2026-09-08 | Job operation request format | Submit job creation requests as `multipart/form-data` with the image in the `image` file field, the operation in the `operation` text field, and the operation-specific options as a JSON-encoded object in the `options` text field. Parse `options` before applying the operation schema so validated data contains a normalized options object. | Preserve the `{ operation, options }` structure defined by the V1 scope while allowing the image and its operation data to be submitted in one request. |
| 2026-09-08 | Maximum resize dimensions | Require both requested resize dimensions to be integers from 1 through 4096 inclusive. | Support common output sizes, including 4K output, while placing a reasonable V1 bound on memory-intensive enlargement. |
| 2026-09-08 | Job file metadata | Store only Cloudinary `publicId` and `secureUrl` for each original and processed image. Require original-file metadata for every job and processed-file metadata when a job is completed. | Retain the minimum identifiers needed to manage and retrieve V1 assets without persisting unused Cloudinary response fields. |
| 2026-09-08 | Job status lifecycle | Allow only `pending`, `processing`, `completed`, and `failed`; default new jobs to `pending`; require output metadata for completed jobs and an error message for failed jobs; do not enforce status-to-status transitions in model hooks. | Preserve the required V1 lifecycle and state integrity while leaving transition orchestration to the future worker. |
| 2026-09-09 | Queue retry and cleanup | Enqueue only the persisted MongoDB job ID. Give image-processing jobs 3 total attempts with exponential backoff beginning at 1 second. Retain completed BullMQ records for up to 24 hours with a maximum of 100, and failed records for up to 7 days with a maximum of 500. | Provide limited recovery from transient failures and enough recent queue history for portfolio-scale debugging while keeping Redis storage bounded; MongoDB remains the authoritative job record. |
| 2026-09-10 | Cloudinary storage and access | Store original and processed images using Cloudinary's default `upload` delivery type. Generate collision-resistant public IDs under `pixsolve/originals/` and `pixsolve/processed/`, disable overwriting, and retrieve originals internally through their stored HTTPS `secureUrl`. Defer Cloudinary `authenticated` delivery until a future version. | Keep V1 storage simple, compatible with the approved `publicId` and `secureUrl` Job metadata, and independent of the deferred download-authorization design while preserving authenticated delivery as a future security improvement. |
| 2026-09-15 | Guest job access | Generate a random 256-bit opaque guest access token, return it once after job creation succeeds, and store only its SHA-256 hash on the Job. Protected guest-job endpoints receive the credential through the `X-Guest-Access-Token` header; credentials are not placed in URLs or in the future JWT `Authorization` header. | Protect guest jobs without introducing guest accounts or another signed-token configuration, keep credentials out of URLs, and avoid storing them in plaintext. |
| 2026-09-15 | Guest job creation response | Return HTTP `202 Accepted`, set `Location` to `/api/v1/image-processing/jobs/:id`, and return a safe pending-job representation together with the one-time guest access token. Do not expose original-file metadata or internal queue data. | Clearly distinguish asynchronous acceptance from processing completion while returning only what the guest needs to access the job later. |
| 2026-09-15 | Guest job creation partial failures | Report acceptance only after Cloudinary upload, MongoDB persistence, and BullMQ enqueueing all succeed. On persistence failure, best-effort delete the uploaded original. On queue failure, best-effort delete the database Job and original image. Log compensation failures safely. Use a deterministic BullMQ ID derived from the MongoDB Job ID to prevent duplicate active queue entries. | Provide portfolio-appropriate cross-system consistency without introducing an outbox or distributed transaction. |
| 2026-09-15 | Guest job creation infrastructure errors | Return HTTP `503` with code `JOB_CREATION_FAILED` and message `The job could not be accepted for processing.` when storage, persistence, or queueing fails. | Give clients a stable, sanitized contract without exposing provider or infrastructure details. |
| 2026-09-16 | API versioning | Prefix all V1 API endpoints with `/api/v1`. | Keep the V1 URLs stable if a future incompatible V2 contract is introduced. |
| 2026-09-21 | Guest job retrieval and download | Require `X-Guest-Access-Token` for `GET /api/v1/image-processing/jobs/:id`. Return `401 GUEST_ACCESS_TOKEN_REQUIRED` when it is missing or blank, and use the same concealed `404 JOB_NOT_FOUND` response for malformed IDs, nonexistent guest jobs, invalid credentials, and credentials belonging to another job. Pending and processing responses omit result metadata; completed responses expose only `result.downloadUrl` using the stored Cloudinary `secureUrl`; failed responses expose only the sanitized processing message as `error.message`. Do not expose input metadata, Cloudinary public IDs, credential hashes, user fields, or queue data. | Protect guest-job discovery while giving clients an actionable missing-credential response. Reuse the approved default Cloudinary delivery model without adding a proxy, redirect endpoint, signed URLs, or authenticated delivery to V1. |
| 2026-09-22 | Email delivery | Use Resend as the V1 email provider through one centralized service. Send text and HTML variants for authentication emails and keep provider errors out of client responses. | Support email verification and password recovery with one portfolio-sized provider integration and consistent error handling. |
| 2026-09-23 | Signup and email verification | Create accounts as unverified, store only hashed expiring verification tokens, and require successful email verification before login. | Keep verification credentials out of the database in plaintext and prevent unverified accounts from receiving authenticated access. |
| 2026-09-24 | Access-token authentication | Use configurable, expiring HS256 JWT access tokens sent with the Bearer authorization scheme. V1 does not issue or accept refresh tokens. | Provide the authentication required for Processing History without adding refresh-token persistence, rotation, or revocation infrastructure to V1. |
| 2026-09-25 | Password recovery | Return the same forgot-password response for known and unknown accounts. Use a hashed, expiring, single-use reset token; after reset, require login with the new password and reject access tokens issued before the password change. | Prevent account discovery, avoid plaintext reset-token storage, and make password recovery invalidate earlier authenticated sessions. |
| 2026-09-26 | Authenticated password update | Require a valid access token, the current password, and a confirmed different password. Invalidate previously issued access tokens, do not issue a replacement token, and treat the password-change notification email as best effort. | Confirm account ownership and require an explicit login after a security-sensitive credential change without making notification delivery part of the successful update transaction. |
| 2026-09-26 | Authenticated job creation | When a valid optional access token is supplied, derive ownership from the authenticated user, create an account-owned job, return the same safe asynchronous job representation used for guest creation, and omit the guest credential. Reject client-supplied ownership. | Reuse the existing creation lifecycle while preventing ownership injection and keeping guest credentials exclusive to guest jobs. |
| 2026-09-26 | Job access credential precedence | If an `Authorization` header is supplied for job retrieval, use account authentication and do not fall back to a guest credential when the JWT is invalid. Without an authorization header, use the guest credential contract. Conceal inaccessible jobs with the existing `404 JOB_NOT_FOUND` response. | Keep guest and account access modes isolated and prevent an invalid account credential from silently changing authorization modes. |
| 2026-09-27 | Processing History pagination | Require authentication, filter by the authenticated owner, sort newest jobs first, default to page 1 with 10 jobs, and allow page and limit values from 1 through 50. Return safe job representations and pagination metadata. | Provide deterministic portfolio-sized history navigation without adding search or advanced filtering. |
| 2026-09-27 | Browser origin access | Allow browser API access only from configured HTTP or HTTPS origins and support the required CORS preflight behavior. | Support the separate demo frontend without accepting arbitrary browser origins or deciding the production deployment topology. |
| 2026-09-27 | Authentication rate limiting | Apply one configurable rate limiter to the V1 authentication router and return the standard sanitized rate-limit response after the configured request maximum. | Add basic protection to security-sensitive endpoints without introducing user-specific or distributed rate-limit policy. |
| 2026-09-27 | API documentation | Keep the V1 OpenAPI 3.0.3 document in the repository and serve it together with Swagger UI from the API. Document every implemented V1 authentication and job operation, request, safe response, and common error. | Make the implemented API contract reviewable and usable without introducing a separate documentation service. |
| 2026-09-27 | Frontend architecture and credentials | Build the demo frontend with JavaScript, React, Vite, React Router, and authored CSS. Keep access tokens and the active guest-job credential in `sessionStorage`, never place credentials in URLs, and poll nonterminal jobs according to `docs/frontend-design.md`. | Provide the approved V1 demonstration experience while keeping frontend state session-scoped and avoiding additional application or deployment requirements. |
| 2026-09-28 | Production deployment topology | Serve the Vite frontend from Vercel at `https://pixsolve.org`. Run Caddy, the API, the separate BullMQ worker, and Redis as separate Docker services on one Oracle Cloud Always Free VM. Use `https://api.pixsolve.org` for Caddy's public API origin, MongoDB Atlas Free for MongoDB, Cloudinary for image storage, and Resend for email. | This is the simplest zero-cost topology that preserves the required separate, continuously running API and worker processes. It keeps V1 single-region and single-VM, avoids a serverless redesign, and uses the already selected Cloudinary and Resend providers. |
| 2026-09-28 | Production environment contract | Set `PUBLIC_APP_URL` and `ALLOWED_ORIGINS` to `https://pixsolve.org`; set the Vercel build variable `VITE_API_BASE_URL` to `https://api.pixsolve.org/api/v1`. API and worker use the same currently required backend environment variables because they share the validated configuration module. Keep all secrets outside Git. Configure Resend with the verified `pixsolve.org` sender domain and use `contact@pixsolve.org` as the sender. | Make browser CORS, generated authentication links, frontend API requests, and email sender authentication agree on explicit public configuration without exposing credentials. |
| 2026-09-29 | Frontend authentication persistence | Store the access token and expiry in `localStorage`, synchronize authentication changes across browser tabs, and migrate any existing session-scoped account credential. Continue storing the active guest-job credential only in `sessionStorage`. | Preserve login across tabs and browser restarts while keeping guest-job access scoped to the active tab session. |
